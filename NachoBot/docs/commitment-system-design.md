# 承诺与约定管理设计

日期：2026-10-18。状态：待确认的替代系统设计，尚未实现。

本次代码变更只退役 `promise_cache`。本文不代表新系统已上线，也不代表历史缓存已迁移。

## 1. 目标与边界

让 NachoBot 能准确回答并据此行动：谁向谁承诺了什么、在什么范围有效、是否仍需遵守、依据是哪几条实际消息。

重要承诺不依赖触发词、不因话题切换或普通记忆衰减而消失；无关承诺不挤占当前上下文。撤销、更正与实际履行都有证据。

职责分工：

| 内容 | 权威来源与责任 |
| --- | --- |
| 人物偏好、经历、过去的对话 | 现有人物画像、中期记忆、A_Memorix |
| 已接受且有效的持续限制、约定、承诺 | 新的 CommitmentService 与结构化台账 |
| 到时提醒、调用工具、执行具体动作 | 现有调度器与动作执行器 |
| 系统身份、平台能力与系统规则 | 原有配置、身份与能力契约，承诺不能覆盖 |

不重写 A_Memorix，不给调度器再造一套任务循环，不用普通记忆检索结果直接认定承诺有效。V1 不承诺自动证明任意自然语言约定都被履行。

## 2. 用户看到的行为

- 在某群中说“以后别在本群提我这件事” → 当前轮直接尊重请求；机器人实际发出清楚的接受答复后，建立有具体信息对象与可见范围的持续约定。
- 机器人主动说“我以后叫你小夏” → 实际发出后建立称呼约定。无需强迫用户另发一条“确认”。
- “我们约定明天见吧？” → 只是提议，不能把提议摘要当成已成立的双方约定。
- “昨晚小说里说好了要……” → 引述与故事，不建立现实承诺。
- “以后不用遵守上次那个了” → 只在唯一指向某条、且发言人有权撤销时撤销；含糊时自然追问。
- “明天九点提醒我” → 交给现有预约流程；任务成功创建才可确认已预约，时间到和发出提醒分别记录。
- 普通聊天、没有相关约定时，不展示管理界面或强制用户确认步骤。

## 3. 权威台账

由核心侧 `src/commitments/` 模块持有，在现有 `NachoBot.db` 中增加专用表及单调版本迁移。V1 不新增独立关键词文件缓存或向量库。

建议模块：`models.py`、`repository.py`、`service.py`、`extractor.py`、`context.py`、`storage/migrations.py`。具体文件切分可在实现规格中调整。

服务边界建议提供：`propose(evidence)`、`activate(proposal_id, delivery_evidence)`、`revoke(id, expected_revision, actor, evidence)`、`supersede(...)`、`record_execution_result(...)`、`resolve_context(scope, participants, query)` 和 `list_for_actor(scope, actor)`。所有写操作鉴权、幂等并检查版本；模型不能直接执行任意状态更新。查询“我和你还有什么约定”走有权限过滤的台账查询，不让模型凭普通记忆拼出清单。

未来新增独立 `[commitments]` 开关与来源会话启用范围，初次发布默认关闭，先在明确选定会话验收。不能把 `memory_retrieval` 开关当成承诺开关；适配器绕过 Planner 也不能绕过已启用的承诺检查。未启用时不能声称承诺已被持久保存。

### 3.1 数据

`commitments` 保存当前状态：

| 字段组 | 含义 |
| --- | --- |
| `id / revision / schema_version` | 稳定 ID、乐观并发版本、结构版本 |
| `bot_identity_id / owner_principal / obligor / beneficiary` | 哪个机器人身份、谁有管理权、谁承诺、向谁承诺 |
| `kind` | `constraint` 持续限制、`agreement` 双方约定、`undertaking` 单方承诺；任务只关联现有执行器 |
| `content / topic / condition` | 具体内容、主题、适用条件；条件不能只有无法解释的模型相似度 |
| `scope / visibility` | 私聊、指定群内指定对象等适用范围，以及允许展示的范围，二者分开 |
| `state / valid_from / valid_until / due_at` | 当前状态、有效区间、截止时间；到期不等于履行 |
| `acceptance_evidence / source_event_key` | 成立依据、幂等来源；关联原始消息，不删除人物与时间 |
| `supersedes_id / executor_ref` | 明确替代哪条、关联哪个实际任务或执行结果 |
| `created_at / updated_at` | 审计时间，绝对时间存 UTC，展示按会话时区 |

`commitment_evidence` 保存输入/输出消息的稳定身份、所在流、发言人、时间和必要原文片段。消息身份至少包含平台、聊天流、方向与消息 ID；有核心 row_id 时同时记录，不能假设消息 ID 全局唯一。

`commitment_events` 保存 append-only 状态变更、证据引用、操作者、前后 revision 与幂等键。当前行和事件必须同一事务更新。

`commitment_work_items` 保存待抽取消息水位、待投递接受记录、恢复任务与可选记忆同步任务。唯一键去重，有界重试；工作完成与水位推进同一事务提交。它不是另一个提醒任务表。

### 3.2 状态

`proposed → active → fulfilled / revoked / superseded / expired`。

- `proposed` 只有候选意义，不以“你已经答应”注入。
- 双方约定需要双方清楚的接受证据；机器人单方承诺需要其已投递的明确承诺。
- 到了约定时间但未证实完成，只标记已逾期的待处理承诺；不能自动写成 `fulfilled`。
- `expired` 仅用于有效区间已结束的约定，不替代逾期概念。
- 持续限制没有自动时间衰减，也不能因为“聊天很久没提到”而删除。
- 无法确定指代、权限或冲突的变更放入待消歧工作项，不擅自覆盖当前有效行。
- `fulfilled` 需要可靠执行结果或有权限的当事人明确确认；模型回复“完成了”不是执行证据。
- 明确撤销请求一经鉴权并持久化便立即生效，不等待机器人成功发送确认。
- 更改采用旧条目终止与新条目建立的事务关联；没有足够证据时不做自动替代。

## 4. 建立承诺的链路

### 4.1 输入与提取

在普通消息通过过滤并成功持久化后登记工作项，不在接收预处理阶段写承诺。系统事件、工具返回、转发和引用内容不能冒充当事人的新承诺。

使用有界的新消息批次和必要上下文做语义提取，区分请求、提议、接受、引用、否认、撤销、更正。模型只输出候选内容与可核对的证据引用；发言人、权限、聊天流及机器人身份由服务端已验证数据补齐。不存在固定关键词硬门槛。

建议复用已有 `utils_small` 模型任务组。采用持久游标、同流批处理和单次有界请求，避免每轮重读整个历史。没有新消息不调用模型。V1 先以准确性为准，再依据测量决定批次和超时预算。

### 4.2 接受与投递

回复生成前建立候选；回复生成后提取或检查机器人是否真的表达接受，并关联候选 ID。内部提案对象与回复文本分离，不给用户暴露数据库 ID。

正式激活必须引用实际投递内容和结果：

1. 对最终即将发送的内容识别具体接受语句；不能只信模型输出的 `accepted=true`。
2. 使用现有 `SendReceipt`，仅 `DELIVERED` 可作为当前发送契约下的成功证据；`SUPPRESSED / FAILED / STALE_LEASE` 不能激活。投递成功不等于用户已读，且可靠程度取决于适配器 ACK 能力。
3. 分段回复只认可已成功投递、且包含完整承诺的段；部分失败不能据整份草稿建立承诺。语音仅使用适配器可确认已投递的实际播报文本；未知时不自动成立。
4. 投递事件以稳定幂等键入队，在事务中提交承诺与审计记录；重复回执不重复建立。
5. 发送前持久化待投递关联，发送后补充回执。进程崩溃时通过已持久化发送记录/ACK 对账；证据缺失则保持待核实，不能把未确认草稿当成已发出，也不能擅自重发原回复。

处理新一轮前先检查该流承诺处理水位。上一轮已投递的接受尚未提交时，必须先对账并追赶；超时则不生成依赖“没有承诺”的肯定结论，也不声称已经永久记住。

## 5. 读取、使用与撤销

### 5.1 统一快照

增加独立于 Focus 的不可变 `CommitmentContext`：包含目标流、机器人身份、参与者、台账 scope revision、已解析的承诺 ID/revision、生成时间和完整性标记。

它是同一轮 Planner 与 Replyer 共享的领域上下文，不塞入 Focus handoff，不伪装成普通用户消息，不依赖 Planner 的 reason 转述。

- 在真正调用模型的 prompt 构建处注入，覆盖 ActionPlanner、BrainPlanner、集成规划回复、private/group Replyer 和适配器直达 Replyer。
- Planner 重建消息上下文时必须显式接收快照；外层预先拼一段字符串不算接入完成。
- Replyer 独立使用同一快照；改写、工具续答复用快照，目标身份或流变化则重建。
- Focus 切换使用现有租约，不能将 A 流的承诺上下文带给 B 流。后台工作显式携带 scope，不继承旧 turn 的副作用授权。
- 系统事件可以读取与其动作相关的有效承诺，但不能作为用户身份来建立、接受或撤销承诺。

### 5.2 两类选择策略

持续限制：依据身份、对象、可见范围和结构化条件确定适用性，全部纳入。不能因向量分数低、冷却时间或普通 top-k 而遗漏。

普通约定/承诺：先按权限和 active 状态过滤，再按参与者、条件、期限和主题选择，语义相似度只参与排序。需要回忆时可按 ID 查询原始证据。

V1 为持续限制设置明确数量与内容长度上限，在写入时检查；读快照仍须检查完整性。超预算或状态不可用时不能静默截断后宣称已全部检查，应停止可能违反限制的输出/动作并给出简短、可恢复的说明。普通回忆可以降级，持续限制不能悄悄绕过。

来源原文以引用数据呈现，不能变成新的系统指令。生成时说明有效内容、对象和条件，不必每次向用户朗读完整台账。

### 5.3 发送与执行前检查

发送前校验 scope revision 和实际相关条目的 revision/state；出现撤销、更新、新增适用限制或目标变化，作废旧快照并重建。只检查旧条目的 revision 无法发现新增限制，因此必须检查 scope revision。

与现有 Focus effect permit 协作，在最终发送/动作提交边界做短期 scope 串行化，确定更新和发送的先后顺序；不把数据库事务跨越整个模型调用。并发撤销按该边界线性化，不承诺撤回已经发出的内容。

明确可判定的限制可做确定性检查；开放自然语言约定需语义复核与有界重写，仍不能宣称绝对保证。复核失败或不确定时，不发送可能违约的草稿。语音流式输出必须在可撤回的播报片段之前检查，不能播完才检查。

没有适用承诺时不追加承诺复核模型调用；可确定的规则优先本地检查。候选抽取与语义复核分别计量请求数、输入输出 token 和耗时，不能为了记住少量约定而无条件给每条回复增加一套多轮 Agent。

提醒与任务通过原执行器的真实结果更新状态。承诺本身不授予新的工具能力或额外动作权限。

## 6. 范围、权限与记忆协作

- V1 默认只在来源会话生效。群内约定绑定具体当事人，群成员不能修改他人的私聊约定。
- 同一人不同平台、同群中的不同成员、不同机器人身份都不能按昵称合并。跨平台身份只能来自现有已验证绑定。
- 一方可以撤销机器人为其作出的持续行为约定；涉及他人的双方约定，更改要满足原约定的参与方授权规则。V1 不推断陌生人有代办权限。
- “在所有群里不要透露”可以形成服务端执行的限制，但其私聊原文与原因不得注入群聊 prompt。必须先完成隐藏约束的执行通道；V1 未支持的跨会话承诺不能假装已接受。
- 现有 A_Memorix 跨会话白名单不自动授予承诺跨会话展示或管理权限。若跨会话能力关闭或无法验证，保持来源会话范围。
- A_Memorix 可存审计回忆的异步镜像，附承诺 ID 与 revision；台账为唯一状态权威。镜像丢失不影响 active 状态。
- 镜像中不能持有高于来源范围的可见权限。历史记忆被召回时，必须回查台账；已撤销的“曾经答应”不能重新成为有效约束。V1 可先不做镜像，避免双写复杂性。

## 7. 退役与历史数据

旧代码退出消息接收、后台整理与 prompt 构建链路；删除配置类和模板配置段，清理测试中的过时 mocks。旧 TOML 中遗留段由现有字段加载器忽略，不为它保留运行服务。

保留 `data/promise_cache/` 原始字节，不自动导入为 active。旧摘要丢失了主体与时间语义，raw 也可能缺失接受答复。

未来迁移工具应先产出 dry-run 清单：来源 raw、可验证消息、候选主体与范围、是否存在后续撤销、建议状态及无法确定的原因。默认只生成候选。只有能证明成立、仍有效且权限正确的条目才允许受控激活；反复运行必须幂等。不能仅凭旧 processed 摘要直接激活。

## 8. 实施阶段与验收

### 本次：退役和设计

删除旧接线、实现与配置；保留缓存和无关配置；运行受影响的系统事件、Focus、恢复、上下文与语音路由测试。本次不新增数据库表、不迁移承诺、不修复整个 Planner 的其他上下文问题。

### V1：同会话、可追溯的承诺管理

先完成台账、幂等事件、自然语言候选提取、真实投递激活、撤销/更正、统一快照与最终检查。覆盖普通、直达与恢复路径。跨会话约定与可选 A_Memorix 镜像暂不开放。

验收必须覆盖：

1. 无触发词的明确承诺可成立；引用、否认、提议和含糊答复不误成立。
2. 失败、被抑制、过期 Focus 租约、分段部分失败均不会凭未发出的文本激活。
3. 进程在发送前、发送后提交前重启，能够恢复对账，不重复创建或擅自重发。
4. Brain/HFC 普通轮、集成轮、离线恢复、直达 Replyer、工具续答和语音路径，捕获实际模型请求证明上下文到达，不能只断言构建函数被调用。
5. 新增限制、撤销和发送并发时，scope revision 和提交边界能阻止使用旧快照；Focus A→B 不串流。
6. 群中另一人、同名者、其他平台身份无法更改或读取不属于自己的约定。
7. 长期不提及的持续约定仍有效；到期和到点不被错误记为已履行。
8. A_Memorix 不可用不影响台账；台账不可用或持续限制超预算不会悄悄漏检查。
9. 迁移 dry-run 零写入，重复迁移幂等，旧缓存原样可恢复。

离线测试可验证上述数据与调用契约；自然语言准确性、真实模型请求、适配器投递与流式语音还需要单独运行验收，不能用 mocks 通过代替。

### V2：按证据扩展

确认 V1 的误建立率、漏建立率、撤销时效、模型延迟和快照覆盖率后，再考虑经授权的跨会话约定、管理查询接口与记忆镜像。不要以一次总“命中率”掩盖误建立承诺的问题。

## 9. 待确认的设计取舍

建议采用：独立领域服务 + 现有核心数据库台账；普通记忆负责回忆，台账负责有效性；自然语言自动识别与真实投递成立，只有歧义时追问；V1 限定同会话。

下一步应先确认这些边界，再拆出新的实现规格。本次退役不代表用户已批准替代系统的全部实现细节。
