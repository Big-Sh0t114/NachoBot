# Shared tool result cache policy

`BaseTool.cacheable` defaults to `False`. A tool author may set `cacheable = True` on the concrete class only when reusing its complete model decision and output is safe, including skipping that tool's execution for the repeated request. This is trusted author metadata, not runtime enforcement of freshness or idempotency. The executor does not infer safety from a tool name or from read-only behavior.

The executor considers the full validated, advertised catalog before looking in the result cache, because a cache hit skips the model decision itself. A nonempty catalog is eligible only when every class declares the exact boolean `True` in its own class dictionary. Inherited flags, truthy values, descriptors, unreadable metadata, and an empty catalog are ineligible. Disabled, hidden, prefix-filtered, and malformed tools are removed before this check, so an excluded writer does not prevent caching an otherwise safe query-only catalog.

When any advertised tool is unmarked, the request bypasses both result-cache lookup and storage, even if the model would have selected only a cacheable query. This intentionally means more model decisions and real executions for mixed catalogs; it keeps a possible write decision and its operation on every request. The rule is shared by group, private, context-building, and SDK-wrapped tool catalogs; wrappers receive no implicit opt-in. `cacheable = False` controls only cache reuse and does not prevent direct or model-selected execution.

The executor snapshots eligibility before preparation and only narrows it when a later live catalog check is ineligible. A later return to an all-cacheable catalog cannot restore eligibility during that same request; a fresh request can use the cache after eligibility is again confirmed. The owner cache scope records the current eligibility marker, so policy changes clear stale entries and legacy scopes with unknown eligibility are invalidated. A replaced owner scope also blocks a late request from publishing into a restored, structurally equal scope. The existing completion, schema, context-sensitivity, TTL, and result-bundle checks remain in force. Outcome handling is unchanged: ordinary result prose that describes a failure is not newly classified as a failure by this policy.

The only built-in opt-ins are `SearchKnowledgeFromLPMMTool` and `GetPersonInfoTool`. No flag is added to provider definitions or tool-result payloads, and cache eligibility is not an authorization rule.
