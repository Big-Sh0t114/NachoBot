# Core 线程增长调查

2026-10-13 的只读检查确认了可复现的原生线程保留路径，尚未证明它是历次 Core、QQ 或整机崩溃的共同原因。本轮没有修改生产 Core、依赖、环境变量、设备或系统设置。

## 活进程证据

核对 PID81108 的原生创建时间 `134363473297604584` 后，只使用查询权限读取线程启动地址与模块范围。823 个线程中，713 个启动地址属于 `VCOMP140.DLL`。查询没有失败；结果只保存模块名与数量，没有输出寄存器、内存内容或绝对地址。

启动地址说明线程所属的运行库，不是当前执行栈，也不能单独把所有 OpenMP 线程归因于某个 Python 调用。该进程此前启动约95个线程，本次检查时为823个，原生创建时间未变。

## 真实方法的隔离对照

从当前 `VectorStore.search` 源码提取未修改的方法 AST，在单独进程中使用固定随机种子的合成索引与查询；不导入生产消息系统，不读写真实向量库。四个 Python worker 调用同一实例，保留方法原有的索引锁。

| 对照 | 每个 worker 的 OpenMP 限制 | Python 线程池退出后额外保留线程 |
| --- | --- | --- |
| 原始检索方法 | 32 | 124 |
| 同一检索方法，实验进程中限制为1 | 1 | 0 |
| 只执行同形状单条查询的归一化 | 32 | 0 |

两组检索的四条查询结果，包括标识、次序和分数，完全相同。三组使用同一份源码摘要。归一化对照未复现增长，完整检索复现；原有 Python 锁能够串行查询，但未防止不同 worker 各自保留 OpenMP 线程。

## 可以得出的结论与边界

- 当前长期记忆检索路径足以触发本机 OpenMP 线程增长，与活进程的大量 VCOMP 线程相符。
- 单条在线查询采用受控的原生并行度值得作为修复候选；需要同时检查其他 Faiss 调用点及其线程设置语义，避免影响后台训练或不同调用方。
- 四条合成查询结果相同不是全库精度或长时间稳定性验收。尚未修改生产实现，也未重启 Core 加载试验设置。
- 没有证据证明这就是历史访问异常的唯一原因；不能把 QQ 的 UI Automation 地址候选、Core 的 native crash、TTS 的内存峰值归为同一故障。
- 限制查询线程不能据此宣称解决 TTS 模型加载所需的内存余量。
