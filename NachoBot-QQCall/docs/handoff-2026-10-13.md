## 3. 架构与责任边界

```text
机器人 QQ Kernel
  ↕ 独立 Shim / Agent / 本机认证 IPC
QQCall Bridge + PPAPI AVSDK Host
  ↕ 通话事件、控制、作用域证明
NapCat 或 SnowLuma 适配器
  ├─ 当前适配器 ACL / 唯一全局通话槽
  ├─ QQCall PCM：设备捕获、重采样、发送、播放/排空/取消
  │    ↕ external PCM / output=none
  │  UniversalVC 公共 API：VAD、ASR、匿名说话人
  └─ 原 QQ 会话上下文 → Core 实时入口 → Replyer → Core TTS
                                      ↓
                     适配器作用域校验 → QQCall PCM → QQ
```

| 所有者 | 责任与主要目录 |
| --- | --- |
| QQCall | `agent/`、`native/`、`bridge/`、`host/`、`service/`、`scripts/`：Shim、信令、接听/拒接/挂断、群房间证明、进程管理及代次；`audio/`、`qqcall_pcm/`：QQ 特有底层 PCM。 |
| QQ 适配器 | `NachoBot-Napcat-Adapter/src/qqcall_runtime.py`、`NachoBot-SnowLuma-Adapter/src/qqcall_runtime.py`及发送链：当前平台 ACL、准入、输出作用域绑定。 |
| QQCall 插件 / 通信公共层 | `NachoBot/plugins/qqcall_plugin/`、`NachoBot/ncnk_message/qqcall*.py`：统一配置、指令、关键词+LLM 复审、生命周期与实时声明校验。 |
| Core | 通用 `realtime_ingress` / `realtime_api`、Focus/调度、上下文、Replyer、选模与 TTS。调度器使用平台无关 `realtime_session`，不直接控制 QQ。 |
| UniversalVC | 冻结服务 API、VAD/ASR/说话人管线及其自身配置。此侧不修改 UniversalVC 内部实现，也不替换其模型。 |
| WebUI | 服务启动与进程观察；QQCall 启动与共享 Host 识别。 |

额外约束：

- QQCall 没有独立来电白名单，以当前 NapCat/SnowLuma 黑白名单为准；群与私聊共享一个通话槽。
- 群只加入已存在的房间。直接邀请、成员数或 SDK ACK 不能代替准入/触发/真实入房证明。
- 普通 QQ 文字消息沿用普通调度；只有通过证明的实时语音进入直接 Replyer 路径。senderless 生命周期事件仍进入上下文与普通 Planner 入口。
- speaker 标签是匿名聚类标识，不能对应 QQ 号、作为授权身份，或凭两条日志宣称两人。
- `ready` 表示控制服务就绪；API 健康、SDK ACK、本地 WAV/排空都不能替代远端听到声音的验收。
- 新讲话后的输出受适配器 delivery fence 限制；现设计不承诺已经开始的 LLM 生成立即取消。
- 设备证明有效期仍为 2 秒。不要靠延长期限、取消进程身份检查、无证据释放占用解决故障。
- UniversalVC 是共享服务；挂断只结束 QQCall 自己的会话，停止 QQCall 不应杀共享 API。

详细约定见 [architecture-boundary.md](architecture-boundary.md)。本次变更已跨 QQCall、适配器公共通信层、Core 通用实时机制和 WebUI，不能再描述为单一插件改动。工作区也含其他会话的 UniversalVC 等修改，不能把整个 dirty diff 当成本任务。
